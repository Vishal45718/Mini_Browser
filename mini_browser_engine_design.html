Mini Browser Engine — End-to-End Systems Design Reference

Section 1

Problem Statement

You're building Toy Browser — a simplified, educational rendering engine that takes an HTML string, parses it, applies CSS, computes layout, and paints output to a canvas or terminal. The goal is to understand how Chrome actually works internally, not to replace it.

In Scope
  • Fetch HTML over HTTP (GET only)
  • Parse a subset of HTML tags
  • Build a real DOM tree
  • Parse inline & external CSS
  • CSS cascade, inheritance, specificity
  • Block / inline layout (box model)
  • Painting to a 2D canvas or pixel buffer
  • Basic JS: document.getElementById, .style, .textContent
  • onClick events (mouse click only)
Out of Scope
  • Full JS engine (no V8)
  • HTTPS / TLS
  • Flexbox / Grid layout
  • Tables
  • Shadow DOM, Web Components
  • SVG rendering
  • Images (beyond placeholder boxes)
  • Fonts (use system monospace)
  • Tabs / multi-process model
  • Security sandboxing
  • Accessibility tree

Core constraints

Single-threaded

No worker threads or parallel parsers. One event loop.

No full JS engine

Interpret only a tiny subset via tree-walk or basic eval.

ASCII or SDL output

Terminal ASCII art or SDL/Pygame pixel canvas. No WebGL.

Subset HTML only

Support: html, head, body, div, p, span, h1-h3, a, ul, li, style, script.

Eight components in a linear pipeline. Data flows in one direction — each stage transforms input into a richer representation.

1. Networking layer input

Opens a TCP socket, sends an HTTP/1.0 GET request, reads the response body as raw bytes. Returns an HTML string. No redirects, no cookies, no caching yet.

2. HTML Parser → DOM Tree transform

Tokenizer reads characters and emits tokens: StartTag, EndTag, Text, Comment. A tree builder consumes tokens and builds a tree of Node objects (Element, Text, Document). Error recovery is required — real HTML is malformed.

3. CSS Parser → Style Rules transform

Reads CSS text, tokenizes property-value pairs, parses selectors. Produces a list of Rule{selector, declarations} objects. Handles inline styles, <style> blocks, and linked stylesheets.

4. Style Resolution (Cascade) transform

Walks the DOM. For each element, collects all matching CSS rules, sorts by specificity, applies inheritance, resolves em/% values. Produces a Computed Style Map per node.

5. Layout Engine compute

Takes the styled DOM and computes a box tree. Each box gets x, y, width, height based on the box model: content + padding + border + margin. Implements block formatting context (vertical stacking) and inline formatting context (horizontal flow with line breaking).

6. Render Tree Construction transform

Strips invisible nodes (display:none, head). Maps DOM nodes to render boxes. At this stage you have a clean tree ready to paint — no layout logic, just paint-ready boxes with visual properties.

7. Painter (Rasterizer) output

Walks the render tree in painter's order (backgrounds → borders → text). Fills a pixel buffer. For ASCII output: maps boxes to terminal rows/cols. For SDL: fills rectangles and blits character bitmaps. JS execution can mutate the DOM and trigger a re-paint.

Step-by-Step Roadmap

Six phases, each producing a visible, runnable output. Never move to the next phase until the current one renders correctly.

P1
Phase 1 — Render plain text HTML
Implement: TCP socket fetch → regex/manual tokenizer → flat node list → print text content to stdout.
Output: Running ./browser http://example.com dumps all visible text to terminal.
Skip: No DOM tree yet. Just extract text between tags.
Networking Tokenizer Text extraction
Common pitfall

Trying to parse HTML with regex. It works for 80% of pages, then silently breaks. Build a real character-by-character tokenizer from day one.

P2
Phase 2 — DOM tree with basic tags
Implement: Full tokenizer → tree builder → Node class with children/parent → serialize DOM to indented text.
Output: A printed DOM tree like a browser's DevTools inspector.
Support: div, p, span, h1-h3, a, ul, li, head, body.
DOM Tree Tree builder Error recovery
Common pitfall

Forgetting self-closing tags (br, img, input, meta). Also: not handling malformed HTML (unclosed tags). Chrome has a full error-recovery algorithm. You need a simplified version.

P3
Phase 3 — CSS parsing + style resolution
Implement: CSS tokenizer → rule list → selector matching (tag, class, id) → specificity calculator → cascade → computed style per node.
Output: Each DOM node prints its resolved style: div → {color: red, font-size: 16px}.
Start with: Only inline styles, then add <style> block support.
CSS Parser Specificity Cascade Inheritance
Common pitfall

Forgetting inheritance. Properties like color and font-size inherit from parent if not set. background-color does NOT inherit. Know the list.

P4
Phase 4 — Layout engine (box model)
Implement: Block layout (vertical stacking), inline layout (text flow + word wrap), margin collapsing (simplified), percentage/auto widths.
Output: ASCII canvas showing boxes at correct positions. Each box labeled with its tag.
Algorithm: Top-down pass to assign widths, bottom-up pass to assign heights.
Box model Block layout Inline flow Word wrap
Common pitfall

Margin collapsing is notoriously complex. Two adjacent block margins collapse into the larger one. Most learners get this wrong. Implement a simple version (no negative margins, no float interactions).

P5
Phase 5 — Painting to a visible surface
Implement: Render tree construction → painter's order traversal → fill pixel buffer (SDL/Pygame) or ASCII grid.
Output: A real window showing your test HTML page with colored boxes and text.
Order: backgrounds → borders → text. No stacking contexts yet.
SDL/Pygame Painter's order Pixel buffer
Common pitfall

Not following painter's order correctly causes backgrounds to draw over text. Always: backgrounds → outlines → borders → text. Never text first.

P6
Phase 6 — Basic JS + interactivity
Implement: A tiny JS interpreter (tree-walk evaluator) that supports: variable declarations, function calls, document.getElementById(), .textContent =, .style.color =, addEventListener('click', fn).
Output: Clicking a button changes text color. That's the goal for Phase 6.
JS interpreter DOM API Events Re-paint loop
Common pitfall

Building a full JS interpreter from scratch is a multi-month project. Use an existing minimal interpreter (e.g. Duktape in C, or Python's ast module) and only implement the DOM-binding layer yourself.

Recommended if you want to understand concepts first and paint output to screen quickly.

Option B — Performance-focused (Rust)

Recommended if you want to go deep into systems and build something closer to a real engine.

HTML/CSS ParserRust from scratchTeaches ownership model deeply. Very satisfying.

Why not C++?

C++ is what Chromium uses, but for a learning project it adds memory bugs and build complexity that distract from understanding the browser concepts. Use Rust if you want C++ performance — same speed, far fewer footguns.

Avoid this trap

Don't pick Rust if you haven't used it before. The borrow checker will eat 60% of your time. Start with Python, get the engine working, then port to Rust once you understand every component.

Code Structure

Each folder maps to one pipeline stage. Never let two stages share mutable state — pass data through return values only.

toy_browser/ ├── net/— HTTP fetch, socket management │ ├── http.py — TCP socket, request/response parsing │ └── cache.py — Simple in-memory URL cache (Phase 4+) ├── parser/— HTML and CSS tokenizing + tree building │ ├── html_tokenizer.py — char-by-char state machine, emits tokens │ ├── html_tree_builder.py — tokens → DOM Node tree │ ├── css_tokenizer.py — tokenizes CSS text into chunks │ └── css_parser.py — chunks → Rule objects with selectors ├── dom/— Data structures for the document model │ ├── node.py — Node, ElementNode, TextNode, DocumentNode │ └── selector.py — Selector matching + specificity calc ├── style/— CSS cascade and computed value resolution │ ├── cascade.py — applies rules to DOM, resolves specificity │ └── computed.py — resolves em/%, inherits properties ├── layout/— Box model and flow layout │ ├── box.py — BoxModel dataclass (x,y,width,height,padding,margin) │ ├── block.py — Block formatting context algorithm │ └── inline.py — Inline formatting context, line boxes, word wrap ├── renderer/— Render tree + painting │ ├── render_tree.py — strips invisible nodes, builds paint-ready tree │ ├── painter.py — walks tree in painter's order, fills surface │ └── canvas.py — pixel buffer abstraction (Pygame or ASCII) ├── js_engine/— Minimal JS binding layer │ ├── interpreter.py — tiny expression evaluator (or Duktape binding) │ ├── dom_api.py — getElementById, style, textContent bindings │ └── event_loop.py — click event queue + dispatch ├── tests/ │ ├── test_parser.py │ ├── test_layout.py │ └── html_fixtures/ — test HTML files └── main.py — CLI entry point, wires all stages together

Key design rules

  • Each module has a single parse() or compute() function. No global state.
  • DOM nodes are immutable after construction. Layout produces new BoxModel objects, it doesn't mutate nodes.
  • The JS engine mutates the DOM through a clean API — dom_api.py is the only bridge.
  • Tests run on each module independently — you can test layout without a running network.

Section 6

Key Algorithms & Concepts

Click each concept to expand the explanation.

HTML parsing — tokenization + tree building ▾

Step 1 — Tokenizer (state machine). You read HTML character by character and maintain a state: DATA, TAG_OPEN, TAG_NAME, ATTR_NAME, ATTR_VALUE, etc. Each state transition emits a token or changes state.

Step 2 — Tree builder. Maintains an open-element stack. When you see <div>, push it. When you see </div>, pop everything until you find a matching div and close it. Text tokens become TextNode children of the current open element.

Error recovery. If you see <p><div>, the <div> implicitly closes the <p> because div cannot be inside p in block layout. Your tree builder must know these rules.

CSS cascade & specificity ▾

Specificity is a score: (inline, id, class, tag) — higher wins. id beats class beats tag. Example: #nav .item a = (0, 1, 1, 1).

Cascade algorithm: 1) Collect all rules matching an element. 2) Sort by origin (author > user agent). 3) Sort by specificity. 4) Last declaration wins if equal. 5) Apply to the element.

Inheritance: If a property is not set and it's inheritable (color, font-size, font-family, line-height), copy from parent's computed value. Non-inheritable properties (background-color, border, margin, padding) default to their initial value.

Box model & layout calculations ▾

Every element is a box. Total width = margin-left + border-left + padding-left + content-width + padding-right + border-right + margin-right.

Block layout (vertical flow): Each block child is placed below the previous one. Width = parent's content width (minus margins). Height = sum of children's heights + own padding.

Inline layout (horizontal flow): Inline elements are placed left-to-right. When a line is full, start a new line. Line height = max(font-size) of elements on that line.

Two-pass layout: First pass (top-down) assigns widths (widths depend on parent). Second pass (bottom-up) assigns heights (heights depend on children).

Painting order (painter's algorithm) ▾

CSS defines a specific paint order to ensure correct visual layering. Your painter must follow this order exactly for every render box:

1) Background color → 2) Background image → 3) Border → 4) Children (in source order) → 5) Outline

This is applied recursively for every element. A child's background paints on top of the parent's background — which is why children appear in front.

Stacking contexts (skip for Phase 5): z-index and position: absolute/fixed create new stacking contexts. This is where real browsers get very complex. Ignore for now.

Selector matching ▾

For each DOM element, you check every CSS rule to see if its selector matches. A selector match is true if the selector's conditions all hold:

  • Tag selector: element.tagName == selector.tag
  • Class selector: element.classList contains selector.className
  • ID selector: element.id == selector.id
  • Descendant: element has an ancestor matching left side of selector

Real browsers do this right-to-left (key selector first, then ancestors) for performance. For your toy engine, left-to-right is fine.

Section 7

Minimal Working Examples

1 — DOM Node class

from dataclasses import dataclass, field
from typing import Optional, List, Dict

@dataclass
class Node:
    node_type: str  # 'element' | 'text' | 'document'
    tag_name: str = ''
    attributes: Dict[str, str] = field(default_factory=dict)
    text: str = ''
    children: List['Node'] = field(default_factory=list)
    parent: Optional['Node'] = None

    def append_child(self, child: 'Node'):
        child.parent = self
        self.children.append(child)

    def get_attr(self, name: str) -> str:
        return self.attributes.get(name, '')

    # Simple pretty-print for debugging
    def dump(self, indent=0):
        prefix = '  ' * indent
        if self.node_type == 'text':
            print(f"{prefix}[text: {self.text.strip()!r}]")
        else:
            print(f"{prefix}<{self.tag_name} {self.attributes}>")
            for child in self.children:
                child.dump(indent + 1)

2 — Simplified CSS cascade

def specificity(selector: str) -> tuple:
    """Returns (id_count, class_count, tag_count)"""
    ids     = selector.count('#')
    classes = selector.count('.')
    tags    = len([p for p in selector.split()
                   if p[0] not in '.#['])
    return (ids, classes, tags)

def matches(node: Node, selector: str) -> bool:
    s = selector.strip()
    if s.startswith('#'):
        return node.get_attr('id') == s[1:]
    if s.startswith('.'):
        return s[1:] in node.get_attr('class').split()
    return node.tag_name == s

def compute_styles(node: Node, rules: list,
                   parent_styles: dict) -> dict:
    # Inheritable properties copy from parent
    INHERITED = {'color', 'font-size', 'font-family',
                 'line-height', 'text-align'}
    styles = {k: v for k, v in parent_styles.items()
              if k in INHERITED}

    # Collect + sort matching rules by specificity
    matching = [(specificity(r.selector), r.declarations)
                for r in rules if matches(node, r.selector)]
    matching.sort(key=lambda x: x[0])

    for _, decls in matching:
        styles.update(decls)

    # Inline styles override everything
    if inline := node.get_attr('style'):
        for decl in inline.split(';'):
            if ':' in decl:
                k, v = decl.split(':', 1)
                styles[k.strip()] = v.strip()

    return styles

3 — Block layout (simplified)

@dataclass
class Rect:
    x: float; y: float
    width: float; height: float

def layout_block(node: Node, styles: dict,
                 container: Rect) -> Rect:
    ml = float(styles.get('margin-left', 0))
    mr = float(styles.get('margin-right', 0))
    pl = float(styles.get('padding-left', 0))
    pr = float(styles.get('padding-right', 0))
    pt = float(styles.get('padding-top', 0))
    pb = float(styles.get('padding-bottom', 0))

    # Width: fill container minus margins
    content_w = container.width - ml - mr - pl - pr
    content_x = container.x + ml + pl
    content_y = container.y + pt

    # Layout children vertically
    cursor_y = content_y
    for child in node.children:
        child_box = layout_block(child, child_styles,
            Rect(content_x, cursor_y, content_w, 0))
        cursor_y += child_box.height

    height = cursor_y - content_y + pb
    return Rect(container.x + ml, container.y,
                content_w + pl + pr, height + pt + pb)

4 — ASCII painter (for terminal rendering)

CANVAS_W, CANVAS_H = 80, 40
canvas = [[' '] * CANVAS_W for _ in range(CANVAS_H)]

def fill_rect(x, y, w, h, char='█'):
    for row in range(int(y), min(int(y+h), CANVAS_H)):
        for col in range(int(x), min(int(x+w), CANVAS_W)):
            canvas[row][col] = char

def draw_text(x, y, text):
    row = int(y)
    if 0 <= row < CANVAS_H:
        for i, ch in enumerate(text):
            col = int(x) + i
            if 0 <= col < CANVAS_W:
                canvas[row][col] = ch

def paint(render_box):
    b = render_box
    fill_rect(b.x, b.y, b.width, b.height, '░')
    if b.text:
        draw_text(b.x + 1, b.y, b.text)
    for child in b.children:
        paint(child)

def print_canvas():
    for row in canvas:
        print(''.join(row))

Section 8

Stretch Goals

These are real features to add once your Phase 1-6 engine is solid. Each one is a deep rabbit hole on its own.

Flexbox layout

Implement the flexbox algorithm: main axis distribution, cross axis alignment, flex-grow/shrink. A 2-3 week project on its own. Read the CSS Flexbox spec — it's unusually readable.

Incremental layout

Instead of full re-layout on every JS change, only re-layout the subtree that was mutated. Requires tracking "dirty" flags on nodes. This is what real browsers do for performance.

Event loop

A real browser event loop: task queue + microtask queue + animation frame callbacks. Implement setTimeout, requestAnimationFrame, and Promise resolution order correctly.

HTTP cache

Implement Cache-Control, ETag, and If-None-Match. This teaches how browsers avoid re-downloading unchanged resources and is a complete mini-project in itself.

CSS custom properties

Implement CSS variables (--my-color: red + var(--my-color)). Teaches how cascade works at a deeper level. Surprisingly straightforward to add once your style engine is clean.

Stacking contexts

Implement z-index and positioned elements. Requires painting in stacking context order instead of source order. Makes transforms and opacity work correctly.

Image loading

Decode JPEG/PNG from file or HTTP, scale to fit the img element's box, and blit to canvas. Introduces async resource loading.

Accessibility tree

Build a parallel tree of accessible nodes (ARIA roles, labels, descriptions). Teaches you how screen readers interact with browsers at the OS level.

Section 9

Learning Strategy

What to learn before starting

Data structures

Trees, stacks, queues. You'll use all three in the first week. Not optional.

State machines

The HTML tokenizer is a 72-state machine. Understand how to model state as an enum.

TCP/HTTP basics

What is an HTTP request/response? Read RFC 7230, sections 1-3. Takes 2 hours.

Box model

Open DevTools right now. Inspect the box model tab for 3 elements. Know this cold.

CSS specificity

Play the CSS Diner game to completion. Then read the MDN specificity page.

Recursion

Every DOM traversal is recursive. If recursion is shaky, fix it now. 2-3 practice problems.

What to deliberately ignore

  • The full HTML5 spec — 1,200 pages. You need maybe 80 pages of it. Focus on section 8 (parsing) and section 12 (tree construction).
  • CSS Grid — More complex than Flexbox. Skip until you have Flexbox working.
  • Security — CORS, CSP, sandboxing. Real browsers need this. Yours doesn't.
  • Multi-process architecture — Chrome uses separate processes for each tab. Out of scope.
  • Font rendering — Kerning, hinting, ligatures, bidirectional text. Use a monospace bitmap font and ignore the rest.

How to debug this system

Each stage has a natural inspection point. Build a --debug flag that prints each stage's output before proceeding:

  • Tokenizer: Print every token as it's emitted. Compare against your expected token list manually.
  • DOM tree: Print the tree as indented HTML. Compare against Chrome's DevTools Elements panel.
  • Computed styles: Print each node's full style map. Compare against Chrome's Computed Styles tab.
  • Layout: Print each box's (x, y, width, height). Compare against Chrome's box model inspector.
  • Painter: If something doesn't show up, add a red debug border around every box to see what's there.
Best reference
Matt Brubeck's "Let's build a browser engine!" blog series (in Rust). It covers Phases 1-4 step by step. Even if you use Python, the logic maps exactly. Read it alongside building.

Section 10

Honest Advice

Why browser engines are genuinely hard

Chrome is one of the largest software projects in history — 35+ million lines of code, maintained by hundreds of engineers. The difficulty isn't in any single algorithm being complex. It's that there are thousands of edge cases that interact with each other. Every CSS property can interact with every other CSS property. HTML error recovery is a spec of its own. The JS engine interacts with layout which interacts with painting which interacts with events.

Your toy engine will handle 20% of cases correctly. That 20% will teach you 80% of what there is to know. That's the right trade-off.

Where most beginners fail
They try to support everything before anything works. They build a "complete" CSS parser before their HTML parser works. They add JavaScript before layout is correct. Ship each phase. A working Phase 1 is worth more than a broken Phase 4.
Second failure mode
Treating real HTML as your test input too early. Start with HTML you write yourself — 10 lines, no external CSS, no JavaScript. Real-world HTML is malformed in ways that will break your engine before you understand your own code.
Third failure mode
Skipping tests. A layout regression 3 phases in will waste more time than writing tests now. Write one test per function, especially for the parser and cascade logic. Layout bugs cascade (no pun intended) through every downstream component.
How to stay consistent
Set a fixed rule: one module per week, in phase order. No phase skipping. Every Friday: demo the current phase output to someone (even yourself via a video recording). This forces you to have something runnable at all times.
The right mindset
You are not building a browser. You are reverse-engineering one to understand it. Every time you get something wrong, you're learning a real browser constraint. The bugs are the learning. Embrace them.
